**picoCRSFbaudRedicer** — преобразователь скорости линии CRSF на Raspberry Pi Pico (RP2040).
Он стоит между приёмником Crossfire/ExpressLRS и полётником: читает CRSF на одной скорости,
проверяет кадры и отдаёт их на другой. Никакой интерпретации протокола — байты кадра
передаются как есть, меняется только скорость линии.

## Задача

Приёмник отдаёт CRSF на **400 кбод** (у ExpressLRS — 420 кбод), а полётник настроен на
**200 кбод**. Скорость на приёме и на передаче должна отличаться, а содержимое кадров —
остаться тем же: CRC в CRSF считается по содержимому, к времени прихода байтов отношения не
имеет.

| Сторона | Скорость по умолчанию | Откуда взята цифра |
| --- | --- | --- |
| Приёмник → Pico | **420000** | ExpressLRS. Ровно это же значение в [biba](https://github.com/GOODWORKRINKZ/biba) (`BIBA_CRSF_BAUD = 420000`), где приёмник заведомо работает |
| Pico → полётник | **200000** | как настроено на стороне полётника (см. предупреждение ниже) |

**Про «400 кбод» и «200 кбод» — это не точные цифры, и вслепую не заработает.**
Стандартные скорости CRSF: **400000** (TBS Crossfire Rev7, [TBS spec](https://github.com/tbs-fpv/tbs-crsf-spec/blob/main/crsf.md)),
**416666** (CRSF Rev10), **420000** (ExpressLRS, [Betaflight `crsf_protocol.h`](https://github.com/betaflight/betaflight/blob/master/src/main/rx/crsf_protocol.h)).
Разница между 400000 и 420000 — это 5 %: UART такое не прощает, полётник будет получать мусор
и уйдёт в failsafe. Поэтому скорость приёмника нужно знать точно, а подобрать её можно
**на лету** из USB-консоли, без пересборки прошивки (см. «Подбор скоростей на лету»).

**Внимание по 200000 на выходе:** 200000 **не входит** ни в один стандартный список CRSF
(в EdgeTX список скоростей модуля: 115200 / 400000 / 921600 / 1870000 / 3750000 / 5250000).
Если полётник на самом деле ждёт стандартную скорость — ставь 400000 (или 420000 для ELRS).
Значение по умолчанию 200000 оставлено таким, как задано по задаче; проверь на железе
и при необходимости смени одной командой.

## Что именно делает прошивка

1. **Собирает кадры.** В потоке ищется sync-байт `0xC8`, затем длина кадра, затем тело;
   CRC8 (DVB-S2, полином `0xD5`) считается на лету.
2. **Проверяет.** Кадр с неверной длиной или CRC отбрасывается и считается в
   `frames_bad` — мусор и обрывки в полётник не идут.
3. **Кладёт целые кадры в очередь** (по умолчанию 32 слота по 64 байта).
4. **Отдаёт целыми кадрами** на второй UART. Если очередь переполнилась, вытесняется
   **самый старый** кадр (`frames_dropped`): для RC свежая команда важнее запоздалой.
5. **Прореживает по свежести.** Новый кадр **заменяет** в очереди более старый кадр
   того же типа: в очереди всегда лежит самая свежая команда RC, а кадры других типов
   (линк-статы, батарея) не вытесняют друг друга. Это ровно то, что нужно для RC:
   запоздалая команда хуже, чем её отсутствие. Отключается `CRSF_BAUD_COALESCE = 0`.
6. **Не залипает на шуме.** Ложный sync-байт в линии запускает сборку
   несуществующего кадра; по таймауту (20 мс) кандидат отбрасывается, а хвост от
   последнего sync-байта сохраняется — настоящий кадр, начавшийся внутри ложного,
   доходит до полётника. После битого CRC мост ресинхронизируется по следующему
   sync-байту и следующий кадр не теряет.

Логика моста — портируемый C без железа (`firmware/src/crsf_baud_bridge.c`), она покрыта
нативными тестами; `main.cpp` держит только UART и индикацию.

## Распиновка (Raspberry Pi Pico)

| Назначение | UART | GP | Примечание |
| --- | --- | --- | --- |
| CRSF от приёмника (вход) | UART1 RX | **GP9** | TX приёмника сюда |
| CRSF к полётнику (выход) | UART0 TX | **GP4** | вход CRSF полётника сюда |
| Обратный канал (опция) | UART0 RX | **GP5** | телеметрия полётника → приёмник, по умолчанию выключено |
| Обратный канал (опция) | UART1 TX | **GP8** | ответ приёмнику |
| Логи/диагностика | USB CDC | — | `Serial`, 115200 |
| Светодиод | GPIO | **GP25** | мигает при приёме кадров |

Пины можно переопределить (`CRSF_BAUD_IN_RX_PIN` и остальные — см.
[docs/configuration.md](docs/configuration.md)).

**GP0/GP1 не используются:** на Pico это выводы USB (D+/D−), и в варианте
`rpipico` ядра Arduino-Pico там по умолчанию сидит `Serial1`. Линии CRSF
уведены на свободные GP4/GP5 и GP8/GP9.

**Уровни.** CRSF — это 3.3 V ([TBS spec](https://github.com/tbs-fpv/tbs-crsf-spec/blob/main/crsf.md),
[Betaflight `crsf_protocol.h`](https://github.com/betaflight/betaflight/blob/master/src/main/rx/crsf_protocol.h)):
3.3 V GPIO Pico подходит напрямую, **5 V на вход Pico подавать нельзя** — GPIO RP2040 не
терпит 5 V.

## Сборка и прошивка

```bash
cd firmware
pio run -e rp2040_crsf_baud_reducer          # сборка
pio run -e rp2040_crsf_baud_reducer -t upload # прошивка (picotool)
pio test -e native_test                        # нативные тесты
```

Требуется [PlatformIO](https://platformio.org/). Платформа — форк
`maxgerhardt/platform-raspberrypi`, `framework = arduino`, `board = rpipico`
(не `pico`: другой board id в этом форке тянет другую прошивку Arduino).

## Проверка без железа

Логика моста и разбор команд консоли собираются обычным gcc и прогоняются
нативными тестами (25 тестов: CRC, round-trip кадра, отбраковка битых,
ресинхронизация, таймаут, переполнение очереди, прореживание, счётчики,
команды консоли):

```bash
cd firmware
gcc -std=gnu11 -Wall -Wextra -Wpedantic \
    -DCRSF_BAUD_TEST_STANDALONE \
    -Iinclude -Isrc -Itest/test_support \
    test/test_crsf_baud_bridge/test_main.c \
    src/crsf_baud_bridge.c src/crsf.c \
    -o /tmp/crsf_baud_test && /tmp/crsf_baud_test
```

## Подбор скоростей на лету

USB-консоль Pico (115200) принимает команды — пересборка прошивки не нужна:

```
help                 список команд
status               текущие скорости и состояние
stats                счётчики моста (ok / bad / dropped / coalesced)
baud_in  420000      новая скорость приёмника
baud_out 200000      новая скорость полётника
```

Команда `baud_in 420000` перенастраивает входной UART на лету (пины сохраняются).
Так подбирается фактическая скорость приёмника: включил приёмник, смотришь в логах
`ok=` (кадры идут) — значит скорость верна; `bad=` растёт — скорость не та,
пробуй следующую (400000 / 416666 / 420000).

## Ограничения (честно)

- **Односторонний канал по умолчанию.** Телеметрия полётника обратно в приёмник не идёт,
  пока `CRSF_BAUD_ECHO_ENABLE = 0`. RC это не ломает, но приёмник не получит от полётника
  телеметрию.
- **Входящий поток быстрее исходящего.** 420 кбод на входе против 200 кбод на выходе: в
  установившемся режиме CRSF идёт короткими пачками, поэтому кадры успевают уходить, и
  **частота кадров на полётнике не меняется** (время на кадр в проводе растёт вдвое).
  Если приёмник начнёт лить непрерывный поток, 200 кбод物理 не догонит — очередь
  переполнится; тогда вытесняется самый старый кадр, а кадры одного типа заменяют
  друг друга (остаётся свежайший). Счётчики `dropped`/`coalesced` это покажут.
  Глубина очереди — 8 кадров: при 100 Гц это до 80 мс запаса, дальше начинается
  прореживание.
- **Только CRSF.** Поток, который не является CRSF (другой sync, другой протокол), не
  пройдёт: мост работает по кадрам, а не по байтам.
- **Грязь в линии стоит кадров.** Одна «грязная» посылка (глюх, плохой контакт) —
  это до 20 мс потери кадров (при частоте RC 100 Гц это ~2 кадра, что укладывается
  в таймаут полётника). Дальше мост сам восстанавливается.
- **Кадр длиннее 64 байт** отбрасывается (ограничение спецификации CRSF).

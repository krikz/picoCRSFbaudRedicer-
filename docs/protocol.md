# Что именно пробрасывается

## Формат CRSF

Кадр CRSF ([TBS spec](https://github.com/tbs-fpv/tbs-crsf-spec/blob/main/crsf.md)):

```
┌────────┬──────────┬──────┬───────────┬─────┐
│ Sync   │ Length   │ Type │  Payload  │ CRC │
│ 0xC8   │ len      │ 0x16 │   ...     │ 8bit│
└────────┴──────────┴──────┴───────────┴─────┘
```

- **Sync** — 0xC8 (серийный), либо 0x00 (broadcast), либо адрес устройства.
  В связке «приёмник → полётник» используется 0xC8.
- **Length** — размер кадра минус 2 (то есть Type + Payload + CRC). Допустимый
  диапазон 2…62; вне диапазона кадр отбрасывается. Кадр длиннее 64 байт не бывает.
- **Type** — тип кадра: 0x16 — каналы RC, 0x14 — статистика линии, 0x08 — батарея,
  0x02 — GPS и другие.
- **CRC** — CRC8 DVB-S2 (полином 0xD5, init 0x00, без рефлексии) по Type и Payload.

Контрольное значение CRC-8/DVB-S2 для строки `"123456789"` — **0xBC**
(каталог CRC: poly 0xd5, init 0x0, refin false, refout false, xorout 0x0, check 0xbc).

## Почему скорость можно менять, а содержимое — нельзя

CRC считается по содержимому кадра, а не по времени прихода байтов. Мост
**не трогает байты кадра** — на выходе полётник получает ровно тот же кадр
(побайтово тест `test_frame_roundtrip_is_byte_exact` это проверяет). Единственное,
что меняется, — скорость, с которой эти байты идут по проводу.

Время передачи одного кадра при этом растёт обратно пропорционально скорости:
при 420 кбод кадр в 26 байт занимает 62 мкс провода, при 230 кбод — 113 мкс.
**Частота кадров при этом не меняется** (она задаётся приёмником), поэтому
таймауты полётника по приёму RC-кадров не задеваются.

**Скорости должны совпадать точно.** UART синхронизируется по фронту старт-бита,
дальше биты считает сам, поэтому допустимо расхождение 2–3 %, на границе (4–5 %)
кадры начинают сыпаться. Отсюда требование: скорость на выходе преобразователя —
ровно то, что выставлено на полётнике.

## Что делает мост с кадрами

1. Ищет sync-байт, отбрасывая всё прочее как мусор.
2. Читает длину, проверяет диапазон 2…62.
3. Считает CRC8 по накопленному кадру.
4. Кадр с верным CRC кладётся в очередь целиком; с неверным — отбрасывается,
   мост **ресинхронизируется по следующему sync-байту** (следующий кадр не теряется).

## Прореживание (свежесть кадров)

Очередь хранит целые кадры. По умолчанию (`CRSF_BAUD_COALESCE = 1`) новый кадр
**заменяет** в очереди более старый кадр **того же типа**:

- RC-кадры (тип 0x16) — в очереди всегда самая свежая команда;
- кадры других типов (линк-статы 0x14, батарея 0x08, GPS 0x02) не вытесняют друг
  друга и доходят как есть.

Зачем: для RC запоздалая команда хуже, чем её отсутствие, — а телеметрию терять
не надо. Если вытеснение не нужно (например, важна вся история кадров), выключается
`CRSF_BAUD_COALESCE = 0` — тогда при переполнении вытесняется просто самый старый кадр.

## Таймаут неполного кадра

Ложный sync-байт в шуме (глюх, плохой контакт) запускает сборку «несуществующего»
кадра: мост ждёт, пока наберётся длина из байта после sync. Чтобы линия не
залипала, хост вызывает `crsf_bridge_expire()`, если входящих байт не было дольше
`CRSF_BAUD_FRAME_TIMEOUT_MS` (по умолчанию 20 мс — больше интервала между
кадрами ~10 мс). По таймауту незавершённый кандидат отбрасывается, но хвост
от последнего sync-байта сохраняется: настоящий кадр, начавшийся внутри ложного,
не теряется.

Цена ошибки: одна «грязная» посылка в линии стоит до 20 мс потери кадров
(при частоте RC 100 Гц это ~2 кадра, что укладывается в таймаут полётника).

## Направление данных и полоса линии

**Схема односторонняя.** Используется только TX приёмника: у приёмника
нет телеметрии, RX-сторона не подключена. Полётник в эту сторону ничего
не шлёт.

```
приёмник TX ──(CRSF, 420000)──▶ Pico ──(CRSF, 230400)──▶ полётник RX
                              (вход)        (выход)
```

Отсюда главное для скоростей: **выходная линия несёт ВСЁ, что пришло от
приёмника.** Если выходная скорость ниже входной, она должна ещё успевать
отдавать поток — иначе кадры вытесняются из очереди.

### Сколько места нужно на линии

UART 8N1 = 10 бит на байт, поэтому байт/с = бод / 10:

| Скорость | Ёмкость линии |
| --- | --- |
| 420000 бод (вход) | 42 000 байт/с |
| 230400 бод (выход) | 23 040 байт/с |
| 400000 бод | 40 000 байт/с |
| 416666 бод | 41 666 байт/с |

Типовой кадр CRSF с каналами RC (тип 0x16) — **26 байт**, статистика
связи (0x14) — 14 байт, батарея (0x08) — 14 байт.

ELRS в режиме CRSF шлёт кадры RC пачками по расписанию радиолинии.
Грубая оценка: при 150 кадрах RC/с это 150 × 26 ≈ 3 900 байт/с — это
**17 % от 230400** и 9 % от 420000. То есть 230400 на выходе — с большим
запасом.

Но это оценка, а не измерение. Поэтому прошивка **считает реальную загрузку
линии** и показывает её в статистике:

```
crsf: ok=1200 bad=0 merged=800 dropped=0 in=4200 out=3900 q=1/8 uart_ovf=0 disc=0
  линия: вход 4200 Б/с (10 % от 420000 бод), выход 3900 Б/с (17 % от 230400 бод)
```

Если процент на выходе дошёл до 90+, скорости не хватает — выводится
предупреждение, и стоит поднять выходную скорость командой `baud_out N`.

### Если позже понадобится обратный канал

Схема уже поддерживает двусторонний режим (телеметрия с полётника
приёмнику): включается `CRSF_BAUD_ECHO_ENABLE=1`. Обратные кадры идут
через **отдельный** мост — проверяется CRC, работает прореживание по типу,
свои счётчики. Скорости по-прежнему независимы: полётник говорит на
`CRSF_BAUD_OUT`, приёмник принимает на `CRSF_BAUD_IN`.

В односторонней схеме обратный канал включён быть не должен: полётник
ничего не шлёт, а UART всё равно надо вычитывать, иначе его FIFO
переполняется. Прошивка вычитывает его всегда, а байты, которые некуда
пересылать, считает в `disc=`.

## Чего мост не делает

- Не меняет содержимое кадров (CRC, типы, payload).
- Не разбирает payload RC-кадров (не знает, где каналы, — это не нужно для
  преобразования скорости).
- Не работает с потоком, который не CRSF (другой sync/протокол) — такие байты
  будут отброшены как мусор.
- Не добавляет и не удаляет кадры: состав потока на выходе совпадает с входом
  (кроме отброшенных битых и вытесненных при переполнении).
